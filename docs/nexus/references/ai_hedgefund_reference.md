## 사례 1. 현직 AI 헤지펀드 개발자의 운영 사례 (2026-10-14 수집)

- 출처: 현직 AI 기반 헤지펀드 개발자가 공개한 글과 조직도 스크린샷(대시보드 갱신 2026-10-12). 작성자·원문 URL은 사용자가 별도로 보관한다.
- 성격: 외부 사례의 요약이다. 글 안의 Robeco 시리즈와 대형 헤지펀드 사례는 이 문서에서 검증하지 않았다.
- 용도: Nexus Trading 구조를 점검할 때 참고한다. 운영 규칙(`docs/nexus/README.md`)과 충돌하면 README를 따른다.

### 1. 글의 요지 (요약)

1. 모델이 좋아질수록 과거에 놓친 오류가 더 발견되어 완료 시점은 오히려 늦어진다.
2. 구독료가 월 100만 원 이상인데도 토큰이 부족해, 남은 토큰에 따라 에이전트 수를 자동 조절하는 에이전트를 만들어 주간 한도의 97~100%를 사용한다.
3. 월가의 방향은 LLM으로 알파를 직접 찾는 것이 아니라 "문헌 연구 → 백테스트 → 결과 평가 → 전략 적용"이라는 퀀트 리서치 프로세스를 자동화하는 것이다 (Robeco "Agentic AI and Alpha" 시리즈를 근거로 언급).
4. 멀티매니저 팟 구조의 대형 헤지펀드는 팀마다 데이터·백테스트 방법론이 달라 비용이 중복되고 품질 관리가 어렵다. 해법은 데이터 중앙 통합과 표준화된 AI 백테스트다.
5. 작성자는 1인이라 처음부터 데이터와 리서치 프로세스를 통합하는 설계가 가능했다.
6. AI가 모든 것을 해결하지는 않으며 도메인 지식과 검증 역량이 여전히 중요하다. 소수의 인원과 LLM 비용으로 과거 대규모 조직의 일을 시도할 수 있다.

### 2. 그 시스템의 구조

- 흐름: CIO 산하 리서처 에이전트가 논문을 분석해 전략 정의 → CTO 에이전트가 구현·백테스트 → CRO 에이전트가 결과를 검증하고 채택 여부 판단.
- 데이터: SQL 기반 중앙 관리, DuckDB와 Polars 사용. 백테스트 약 10초, LLM 결과 평가 1~2분.
- 조직도(스크린샷 기준): CEO(대표 에이전트) 아래 CIO, CRO, CTO 라인. 리서치 팀들은 CIO 쪽, 리스크·검증 팀은 CRO 쪽, 데이터 엔지니어링·인프라·백테스트 엔진·일회성 러너는 CTO 쪽. 검증 담당("리서치 검증관")이 구현 라인과 별도 라인에 있다.
- 모델 혼용: Opus, Sonnet, Haiku, GLM, GPT 등. 계정을 여러 개 두고 주간 사용량을 대시보드로 감시한다.

### 3. Nexus Trading에 대한 시사점

| 항목 | 사례 | 우리 쪽 상태 / 검토 |
|---|---|---|
| 구현과 검증 분리 | CTO와 CRO 라인 분리 | 독립 검증 에이전트 도입(일치) |
| 검증의 보고 라인 | CRO가 CTO·CIO와 별도 | Validation이 CIO 밑에 있어 일정 압박이 검증에 영향을 줄 여지. 보고 라인 분리 검토 |
| 모델 다양성 | 모델 혼용 | Validation을 Gemini로 구성(일치) |
| 중앙 데이터 계층 | SQL + DuckDB/Polars, 백테스트 약 10초 | 로드맵 첫 슬라이스에 PIT 정합성·생존편향 없는 유니버스를 데이터 계층에서 보장하는 항목 검토 |
| 빠른 백테스트의 과적합 위험 | 반복이 매우 쉬움 | 시도 횟수 기록, 홀드아웃 1회, 결과를 보고 파라미터 조정 금지(체크리스트 E·F)를 자동 루프에서도 강제 |
| 토큰 한도 | 한도의 97~100%를 사용하도록 에이전트 수 자동 조절 | Claude Max 5x를 다른 작업과 공유. 시작은 Dev의 Max turns를 낮추고 사용량부터 관찰 |
| 조직 규모 | 수십 개 에이전트 | 4명으로 시작. 첫 개발-검증 루프가 동작한 뒤에 확장 |
